# 2인 분담 — 역할표 (확정안)

> 교안 종합 실습(HelpDesk AI, p.307–322)을 학사 안내 도메인(SKALA University)으로
> 구현한다. 원본 사고 과정과 배경은 `skala-springai` 리포의
> `docs/SpringAI-이해-및-활용_Day3_2026-08/04_종합실습_2인분담_가이드.md` 참조.

전문 영역은 나누되, **상대 기능을 반드시 리뷰하는 구조**다. 실무처럼 책임자를 두면서도
학생 프로젝트에서 한 사람만 특정 기술을 아는 상황을 방지한다.

## 역할 구성

- **A: AI·RAG·플랫폼 담당**
- **B: 업무 API·Tool·보안 담당**
- **공통**: 설계 결정, 통합 테스트, PR 리뷰, 배포

담당자는 혼자 결정하고 구현하는 사람이 아니라 해당 기능의 **첫 번째 책임자**다.
상대방은 **두 번째 담당자**로서 반드시 코드 리뷰와 실행 검증에 참여한다.

---

## A — AI·RAG·플랫폼 담당

### 주요 책임

A는 "AI가 정확한 근거로 답하고 안정적으로 운영되는 과정"을 책임진다.

```
모델 설정 → 문서 인제스트 → 벡터 검색 → RAG 답변 → 대화 메모리 → 토큰·지연 측정 → 폴백
```

### 담당 파일

```
config/
├── AiConfig.java
└── HelpDeskProperties.java

rag/
└── IngestService.java

chat/
└── HelpDeskService.java

advisor/
├── TokenMeterAdvisor.java
└── SafeGuardAdvisor.java

src/main/resources/
├── application.yml
├── prompts/
└── helpdesk-docs/
```

### Phase별 업무

**Phase 1** (p.313) — OpenAI Chat·Embedding 설정 · pgvector 설정 · `HelpDeskProperties`
구현 · `ChatClient` 조립 · Advisor 순서 결정 · 시스템 프롬프트 관리.

**Phase 2** (p.314) — 문서 읽기 · 청크 분할 · 문서 재색인 · 메타데이터 추가 ·
`VectorStore` 저장. 필수 메타데이터: `source`, `docType`, `dept`, `version`.

**Phase 3** (p.316) — RAG 답변 생성 · 검색 문서 추출 · 실제 사용한 출처 반환 · 출처
중복 제거 · 근거 없음 처리.

**Phase 5** (p.319) — JDBC 대화 메모리 · 최근 20개 메시지 윈도우 · `conversationId`
생성 · 테넌트·학번·세션 격리.

**Phase 6** (p.320) — 스트리밍 서비스 로직 · 요청 단위 출처 관리 · 스트리밍 취소 전파 ·
60초 타임아웃 처리 지원.

**Phase 7** (p.310) — `SafeGuardAdvisor` · 민감어 차단 · 직접·간접 프롬프트 인젝션
방어 · 안전 필터가 메모리보다 앞에 있는지 검증 · 차단된 입력이 메모리에 남지 않도록
처리.

**Phase 8** — 토큰 측정 · 모델 응답 지연 측정 · AI 오류 카운터 · 모델 폴백 · 비용 상한
관리 · AI 관련 Micrometer 지표.

### A의 완료 기준

- 검색 결과에 답이 있는지 직접 확인함.
- 규정 답변에 실제 출처가 있음.
- 근거가 없으면 추측하지 않음.
- 학번·세션 간 메모리가 섞이지 않음.
- 토큰과 모델 지연을 측정할 수 있음.
- 주 모델 장애 시 폴백 경로가 동작함.

## B — 업무 API·Tool·보안 담당

### 주요 책임

B는 "사용자가 안전하게 API를 사용하고 실제 업무 작업을 수행하는 과정"을 책임진다.

```
인증 → API 요청 → 학적 조회 → Tool 실행 → 권한 검증 → 수강철회 접수 → 감사 기록 → API·보안 테스트
```

### 담당 파일

```
web/
├── ChatController.java
├── AdminController.java
└── SecurityConfig.java

tools/
├── AcademicTools.java
└── RequestTools.java

repository/
├── StudentRecordRepository.java
└── WithdrawalRequestRepository.java

chat/
└── AnswerDto.java

advisor/
└── AuditAdvisor.java

eval/
└── GoldenSet.java

http/
└── samples.http
```

### Phase별 업무

**Phase 1** (p.313) — Docker Compose 실행 확인 · `.env.example` 관리 · Health 확인 ·
Swagger 확인 · 실행 방법 README 작성 · 감사 Advisor 기본 골격 작성.

**Phase 2 심화** (p.315) — 관리자 검색 확인 API · 청크 검색 결과 DTO · 관리자 권한
적용 · 중복 인제스트 테스트 · 검색 결과의 점수와 미리보기 확인.

**Phase 3** (p.316) — `AnswerDto` 계약 · `Source` DTO · Controller 요청·응답 · 입력
검증 · RAG API 테스트 · Swagger 응답 예시.

**Phase 4** (p.317) — `StudentRecordRepository` · 학적 조회 Tool(`myCourses`·
`gradStatus`) · 수강철회 접수 Tool(`requestDrop`) · 학번 소유자 검증 · `ToolContext`
사용자 정보 사용 · 승인 대기 신청 처리.

**Phase 5** (p.319) — 3턴 시나리오 테스트 · 학번별 메모리 격리 테스트 · 세션별 메모리
격리 테스트 · 재시작 후 메모리 유지 확인 · `conversationId` 위조 테스트.

**Phase 6** (p.320) — 동기 REST API · SSE Controller · `token`·`sources`·`done` 이벤트
· 요청 DTO 검증 · 동시 요청 테스트 · HTTP 호출 샘플 관리.

**Phase 7** — 사용자 인증 · 학사팀 권한 · Tool 내부 권한 검증 · 수강철회 승인 게이트 ·
Tool 호출 감사 로그 · 개인정보(학번·성적) 로그 마스킹 · 레드팀 테스트 10종.

**Phase 8** — Golden Set 실행 도구 · P95 응답시간 측정 · Tool 성공률·오류율 확인 ·
장애 주입 테스트 · 폴백 검증 · 최종 테스트 결과 문서화.

### B의 완료 기준

- 다른 학번의 학적 정보가 조회되지 않음.
- 학번을 프롬프트로 위조할 수 없음.
- 수강철회가 즉시 처리되지 않음.
- 관리자 API를 일반 학생이 호출할 수 없음.
- Tool의 성공과 실패가 감사 로그에 남음.
- 동기 API와 SSE 응답 구조가 일관됨.
- 레드팀 테스트 10종을 통과함.

## 공동 책임

다음 사항은 A 또는 B 혼자 결정하지 않는다.

### API 계약

```java
record AnswerDto(
    String answer,
    List<Source> sources,
    boolean toolUsed
) {}
```

DTO를 변경하려면 두 사람이 합의한다.

### Advisor 순서

```
Audit(0) → TokenMeter(10) → SafeGuard(100) → Memory(200) → RAG(300)
```

A가 `AiConfig`에 반영하고 B가 보안 관점에서 검토한다.

## 파일 충돌 방지 규칙

다음 파일은 소유자를 명확하게 둔다. 상대 소유 파일을 직접 수정해야 한다면 먼저
Issue나 메시지로 알린다.

| 파일 | 최종 소유자 | 상대 역할 |
|---|---|---|
| `AiConfig.java` | A | B가 보안 순서 검토 |
| `application.yml` | A | B가 환경·비밀정보 검토 |
| `HelpDeskService.java` | A | B가 API·권한 관점 검토 |
| `AnswerDto.java` | B | A가 RAG 출처 구조 검토 |
| `ChatController.java` | B | A가 ChatClient 연결 검토 |
| `SecurityConfig.java` | B | A가 Advisor 차단 흐름 검토 |

## PR 리뷰 분담

### A의 PR을 B가 확인

- 관리자 API가 보호되는가.
- 문서 필터에 권한 조건이 있는가.
- 학번별 메모리가 격리되는가.
- 출처에 내부 정보가 노출되지 않는가.
- 환경변수와 비밀정보가 안전한가.

### B의 PR을 A가 확인

- Tool 설명이 모델이 이해하기 쉬운가.
- Tool 결과가 불필요하게 길지 않은가.
- RAG와 Tool을 구분해서 사용하는가.
- Tool 실패가 무한 재호출을 유도하지 않는가.
- 실시간 데이터가 문서 근거처럼 처리되지 않는가.

## 권장 학습 교대

한 영역을 끝까지 한 사람만 맡으면 실무 경험보다 분업 과제가 된다. 다음 시점에 역할을
바꾸어 설명한다.

- Phase 3 완료 후: A가 B에게 RAG 전체 흐름 설명.
- Phase 4 완료 후: B가 A에게 Tool·권한 흐름 설명.
- Phase 6 완료 후: 서로 상대 기능의 테스트 작성.
- Phase 8 완료 후: 상대방 기능을 대신 시연.

**최종 기준**: A가 학적 조회 Tool과 권한 구조를 설명할 수 있고, B가 RAG 검색과 출처
구조를 설명할 수 있어야 프로젝트가 완료된 것이다.
