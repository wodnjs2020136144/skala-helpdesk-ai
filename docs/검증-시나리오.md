# 검증 시나리오 — 완료 시나리오 7종 체크리스트

두 사람이 모두 아래 흐름을 각자 실행해 본다(교안 p.321 다섯 흐름을 학사 도메인으로
치환 + 비기능 요구 2종 추가). 실행 요청 샘플은 `http/samples.http` 참고.

> **Phase 7 이후 재현 방법이 바뀌었다** — 모든 API에 인증이 붙었다. 학번은 요청
> 파라미터가 아니라 인증 주체(`Principal`)에서만 온다. curl로 재현할 때는 Basic 인증을
> 붙인다: 학생은 `-u 2021001:student`, 학사팀은 `-u admin:admin`
> (기본 비밀번호는 로컬 실습 전용 — `HELPDESK_STUDENT_PASSWORD`·`HELPDESK_ADMIN_PASSWORD`로
> 바꿀 수 있다). `?studentId=`를 붙여도 무시된다(시나리오 ⑤ 참고).

## 기록 방법

각 행마다 실행자 이름과 결과(통과/실패 + 응답 캡처 또는 로그 발췌)를 채운다. 실패한
항목은 원인과 수정 커밋을 함께 남긴다.

## 보조 확인

- **인증 경계**(Phase 7) — `/actuator/**`·`/api/admin/**`는 ADMIN만, `/api/chat/**`는
  STUDENT만 접근할 수 있다(`SecurityConfig`).
  - ☑ 실측 확인(2026-08-22, A) — 같은 엔드포인트를 세 주체로 호출해 비교:

    | 엔드포인트 | 미인증 | `-u 2021001:student` | `-u admin:admin` |
    |---|---|---|---|
    | `/actuator/health` | 200 | — | — |
    | `/actuator/metrics/ai.tokens` | 401 | **403** | **200** |
    | `/actuator/prometheus` | 401 | **403** | **200** |
    | `/api/admin/chunks?q=졸업` | 401 | **403** | **200** |

    `/actuator/health`와 Swagger는 의도대로 `permitAll`이다. 한글 쿼리는 셸에서
    `curl -G --data-urlencode "q=졸업"`로 보내야 한다(그냥 URL에 넣으면 400).
- `GET /actuator/metrics/ai.tokens`, `GET /actuator/metrics/ai.latency` — Phase 8 계측이
  쌓이는지 확인(**ADMIN 인증 필요** — `curl -u admin:admin ...`).
  - ☑ 실측 확인(2026-08-22, A) — 정상 질문 1건 후 `ai.tokens`(model=`gpt-4o-mini-2024-07-18`
    태그, prompt/completion 분리), `ai.tokens.cumulative` 게이지, `GET
    /actuator/prometheus`에서 `ai_tokens_total`·`ai_latency_seconds_*` 노출까지 확인.
    SafeGuard 차단 응답은 `ai.tokens` 값이 그대로(변화 없음) — usage가 0인 응답은
    계측하지 않음을 실증.
  - ☑ 비용 상한 경고 실측(2026-08-22, A) — 단위 테스트(`TokenMeterAdvisorTest`)로 검증한
    것과 별개로, `max-total-tokens`를 100으로 임시로 낮추고 재기동해 통합 환경에서도
    재현: 정상 질문 1건 후 `ai.budget.exceeded`=1, 응답은 HTTP 200으로 정상 반환됨을
    확인(요청을 막지 않는다는 설계 의도대로 동작). 확인 후 200000으로 원복.
- **도구 호출 상한**(`helpdesk.tool.max-calls`, Phase 6) — 같은 도구를 무한히 부르는
  함정을 막는 안전장치가 실제로 발동하는지.
  - ☑ 실측 확인(2026-08-22, A) — 단위 테스트(`BoundedToolCallingManagerTest`)와 별개로,
    `max-calls`를 **0**으로 임시로 낮추고 재기동해 통합 환경에서 재현(0이면 도구 호출
    1건도 상한을 넘으므로 확실히 발동한다). 도구를 부르는 질문("제가 지금 몇 학점이죠?")
    → HTTP 500 + 안전 문구·traceId만 반환(내부 예외 미노출), 로그에
    `ToolCallLimitExceededException: 도구 호출 상한(0회)을 초과했습니다 calls=1 batch=1`.
    **배치 크기(batch=1)가 로그에 함께 찍혀** PR #10 리뷰에서 고친 "진입 횟수가 아니라
    도구 호출 개수를 센다"가 통합 환경에서도 동작함을 확인했다.
    - 상한 초과는 **폴백 대상이 아니다** — "폴백 모델로 재시도" 로그 0건,
      `ai.fallback` 지표는 생성조차 안 됨(404). 안전장치가 의도적으로 발동한 것이라
      폴백이 새 카운터로 다시 부르면 상한이 두 배가 되기 때문(설계대로).
    - 메모리도 오염되지 않는다 — `GET /api/chat/history`가 `[]`로, 답변 없는 질문이
      남지 않았다(`HelpDeskService.restoreMemory()` 동작 확인).
    - 확인 후 5로 원복.
- `GET /api/admin/chunks?q=...` — 인제스트된 청크의 source·docType·dept·version·score를
  확인한다(**ADMIN 인증 필요**). 검색 누락 원인을 진단할 때는 `threshold=0&topK=20`처럼
  운영 검색보다 넓게 조회한다(Phase 2 심화, p.315).
- `docker exec -it <pgvector-container> psql -U helpdesk` 후 재기동 — Phase 5 JDBC 메모리가
  재시작 후에도 유지되는지 확인.
  - ☑ 실측 확인(2026-08-22, A) — 3턴(6개 메시지) 대화 후 앱을 종료·재기동하고
    `GET /api/chat/history`로 조회한 결과, 메시지 6개가 그대로 남아 있음(`\dt`로
    `spring_ai_chat_memory` 테이블 존재도 함께 확인).
  - ☑ 20개 윈도우 트리밍 실측(2026-08-22, A) — 같은 세션에서 12턴(24개 메시지)을 보낸 뒤
    조회하니 가장 오래된 4개(2턴)가 잘리고 최근 20개만 남음(`helpdesk.memory.max-messages`
    설정대로 동작).
  - ☑ `conversation_id`별 저장 분리 실측(2026-08-22, A) — DB에서
    `SELECT conversation_id, count(*) FROM spring_ai_chat_memory GROUP BY 1`로 직접 조회,
    학번·세션 조합마다 완전히 분리된 행으로 저장됨을 확인(같은 세션 문자열이어도 학번이
    다르면 별개 `conversation_id`).
- **SSE 이벤트 계약**(Phase 6) — `POST /api/chat/stream`이 `token*` → `sources` → `done`
  순서로 내보내는지, `sources`에 실제 출처가 실리는지, 근거 없음 처리가 동기 API와
  일치하는지.
