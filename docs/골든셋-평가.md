# Phase 8 Golden Set 평가

교재의 결정적 테스트 원칙에 따라 모델 답변 전체 문장을 비교하지 않고, 문항별 핵심 사실과
출처, Tool 사용 여부를 검사한다. 사용자 요구에 맞춰 기준선은 20문항으로 구성했다.

## 문항 구성

| 범주 | ID | 개수 | 검사 내용 |
|---|---|---:|---|
| 학사운영규정 | `AC-01`~`AC-05` | 5 | 신청학점, 정정, 철회, 이의신청 |
| 졸업요건 | `GR-01`~`GR-05` | 5 | 총·전공학점, 어학, 캡스톤, 졸업 사정 |
| 장학금 | `SC-01`~`SC-04` | 4 | 성적 구간, 최소 이수학점, 신청 방식 |
| Tool | `TL-01`~`TL-03` | 3 | 학적 조회, 졸업 상태, 철회 접수 |
| 근거 없음 | `NE-01`~`NE-03` | 3 | 식단, 기숙사 통금, 주차 요금 |

기대 출처가 있는 15문항은 해당 파일이 `sources`에 포함되는지 확인한다. Tool 전용 2문항은
출처를 평가하지 않고 Tool 사용과 핵심 반환값을 검사한다. 근거 없음 3문항은 `sources`가
비어 있고 안전 문구가 포함되는지 확인한다.

## 실행 방법

일반 단위 테스트와 빌드는 실제 모델을 호출하지 않는다.

```bash
./gradlew test
./gradlew build
```

실제 평가는 OpenAI 키와 실행 중인 pgvector가 필요하다. 애플리케이션과 같은 DB 환경변수를
설정한 뒤 아래 태스크를 실행한다.

```bash
export OPENAI_API_KEY="..."
./gradlew goldenSetTest
```

결과는 `build/reports/golden-set/results.md`에 생성된다. 이 파일에는 답변 원문을 남기지 않고
문항별 PASS/FAIL, 지연시간, 실제 출처, 오류 유형만 기록한다. Tool 오류율은 예외 발생뿐
아니라 기대한 Tool 미호출과 핵심 반환값·출처 검증 실패를 포함하며 `1 - Tool 성공률`로
계산한다.

기본 합격 기준은 전체·출처·Tool·근거 없음 각각 80% 이상, 호출 오류 0건,
비스트리밍 P95 5초 이하이다. 필요하면 아래 환경변수로 기준만 재설정할 수 있다.

- `GOLDEN_SET_MIN_PASS_RATE`
- `GOLDEN_SET_MIN_SOURCE_HIT_RATE`
- `GOLDEN_SET_MIN_TOOL_SUCCESS_RATE`
- `GOLDEN_SET_MIN_NO_EVIDENCE_RATE`
- `GOLDEN_SET_MAX_P95_MS`

실제 평가 결과와 Actuator의 `ai.tokens`, `ai.latency`, 모델 폴백 결과는 A의 Phase 8 변경을
현재 브랜치에 반영한 뒤 작업순서 문서와 검증 시나리오에 기록한다.

## 2026-08-22 RAG 검색 교정 — 부칙 분리와 페이지 머리말·꼬리말 제거 (A)

Golden Set의 `AC-01`을 본칙 기준으로 바로잡는 과정에서, **문항이 아니라 검색 쪽에 진짜
문제가 있다**는 것이 드러났다. 교정 전 질문("한 학기에 최대 몇 학점까지 신청할 수
있나요?")을 그대로 던지면 모델이 이렇게 답했다:

> 일반적으로 **23학점**입니다. … 3.5 이상인 경우 3학점을 추가로 … 따라서 최대 **26학점**

부칙의 23학점(1999학년도 이전 160졸업학점제 대상자 특례)과 본칙의 +3학점을 뒤섞은
환각이다. 26학점은 어느 규정에도 없다(본칙 21+3=24, 부칙 23+1=24). `/api/admin/chunks`로
확인하니 정답인 본칙 제12조 ①항이 상위 검색 결과에 아예 들지 못하고 있었다.

질문을 구체화하면 통과하지만 실제 학생이 던지는 짧은 질문에서는 여전히 틀린 안내가
나가므로, 검색 자체를 두 가지로 고쳤다(A 담당 영역).

### ① 본칙/부칙 분리 (`IngestService.splitBySection`)

인제스트 단계에서 첫 부칙 헤더를 경계로 문서를 갈라 `section` 메타데이터(`main` /
`supplementary`)를 붙이고, 운영 검색(`AiConfig`의 `QuestionAnswerAdvisor`)에만
`section == 'main'` 필터를 건다. **부칙을 버리지는 않는다** — 관리자 진단
(`/api/admin/chunks`)은 필터 없이 조회하므로 부칙까지 그대로 보인다.

부칙 헤더 표기가 문서마다 다른 것을 실측에서 발견했다 — `학사운영에관한규칙.pdf`·
`장학금에관한규칙.pdf`는 `부 칙`인데 `한국기술교육대학교_학칙.pdf`는 `<부 칙>`이라
꺾쇠를 빠뜨렸다가 학칙만 분리되지 않았다.

### ② 페이지 머리말·꼬리말 제거 (`IngestService.stripPageFurniture`)

①만으로는 부족했다. 23·26학점 환각은 사라졌지만 이번엔 "18학점"(대학원 편입생 학점
인정 조항)을 잘못 인용했다. 정답 청크를 열어 보니 조문이 이렇게 끊겨 있었다:

```
제12조(수강신청 제한) ① 수강신청 상한 학점은 다음 각 호와 같다. (개정 2021. 4. 1., 2022.
학사운영에 관한 규칙      <- 페이지 머리말
- 4 / 63 -               <- 페이지 꼬리말
3. 1.)                   <- 잘린 개정일 파편
1. 공학사과정: 21학점 이내
```

Tika가 머리말·꼬리말을 본문과 섞어 뽑아 청크 임베딩이 흐려진 것이다. 꼬리말은
`- 4 / 63 -` 꼴이라 패턴으로, 머리말은 문서마다 제목이 달라 **짧으면서(30자 이하) 여러
번(5회 이상) 되풀이되는 줄**을 기준으로 지운다. 섹션 분리 **뒤에** 지운다 — 부칙 헤더도
반복되는 짧은 줄이라 먼저 지우면 경계를 못 찾는다.

### 실측 결과

| | 답변 |
|---|---|
| 교정 전 | "일반적으로 **23학점** … 최대 **26학점**까지" (부칙·본칙 혼합 환각) |
| ① 부칙 분리 후 | "일반적으로 **18학점** … 최대 21학점" (대학원 편입 조항 오인용) |
| ①+② 적용 후 | "**공학사 과정: 21학점 이내**, 경영학사 20학점, 고용학사 20학점 … 직전학기 평점평균 **3.5** 이상이면 최대 3학점 초과 신청" |

현행 본칙을 정확히 인용하고 23·26·18학점이 모두 사라졌다. 청크 수도 군더더기가 빠지며
줄었다(학사운영 167→152, 학칙 142→131, 장학금 18→17).

### `AC-01` 문항은 그대로 둔다

자연어 질문의 답변이 정확해졌지만 **기대 키워드 `24학점`은 여전히 나오지 않는다** —
모델이 "21학점 + 3학점 초과 가능"이라고 규정 그대로 답하고 합계를 계산해 주지 않기
때문이고, 규정 원문에도 "24학점"이라는 표현은 없다. 통과시키려고 질문이나 기대값을 다시
다듬지 않고, 최대 학점을 명시적으로 묻는 현재 문항을 유지한다.

## 2026-08-22 근거 없음 후처리 정밀화 — 정답인데 출처가 사라지던 문제 (A)

PR #11~#15를 모두 머지한 `main`에서 평가를 돌리니 **`AC-01`이 두 번 연속 출처
판정만 실패**했다(핵심 사실은 통과). 검색 교정(#12)이나 인젝션 방어(#13)의 회귀를
의심했지만 아니었다:

- `RetrievalGuard` 차단 **0건** — 과차단이 아니다.
- pgvector 메타데이터 정상(`injected=no`, 본칙/부칙 분리 확인).
- 같은 질문을 앱에 직접 호출하면 **5회 모두** 정답과 출처(`학사운영에관한규칙.pdf`)를
  정상 반환했다.

원인은 `HelpDeskService.sourcesFrom(String, ChatClientResponse)`의 근거 없음 후처리였다.
답변 **어디에든** 표준 문구가 있으면 출처를 통째로 지우고 있었다. 그러면 정답을 말한 뒤
덧붙인 헤지에도 걸린다:

> 공학사과정 학생의 기본 수강신청 상한은 21학점입니다. … **다만 그 외 과정에 대해서는
> 정확한 규정을 확인할 수 없습니다.**

근거를 제대로 인용하고도 출처가 사라져, 사용자에게는 근거 없이 답한 것처럼 보인다. 이
문서 앞 절에서 "문구를 일부 인용하는 답변에서도 출처를 지울 수 있다"고 한계로 적어 둔
것이 실제로 발현한 것이다.

### 조치 — 첫 문장으로만 판정한다

시스템 프롬프트가 "확실하지 않으면 …라고 답하세요"로 지시하므로 근거 없음 응답은 이
문구로 답을 **연다**. 반면 헤지는 본문을 답한 뒤 뒤에 붙는다. 규칙을 정하기 전에 실제
답변을 모아 확인했다 — 근거 없음 문항(`NE-01`·`NE-02`·`NE-03`)을 3회씩 호출해 표준
문구가 나온 **7건 모두 첫 문장**이었다. 그래서 첫 문장에 있을 때만 출처를 지운다.

### 교정 후 재평가 (`goldenSetTest` 3회 반복)

| 회차 | 전체 | 필수 출처 | 근거 없음 | 실패 문항 |
|---:|---:|---:|---:|---|
| 1 | 95.0% | **100.0%** | 100.0% | `SC-04`(핵심 사실) |
| 2 | 95.0% | **100.0%** | 66.7% | `NE-01`(핵심 사실) |
| 3 | 95.0% | **100.0%** | 100.0% | `SC-04`(핵심 사실) |

**출처 적중률이 3회 모두 100%**로, `AC-01`의 출처 실패는 재현되지 않는다. 다만 교정
전에도 `AC-01` 실패를 앱 직접 호출로는 재현하지 못했으므로, 이 교정이 그 실패를 없앴다고
단정하지는 않는다. 확실한 것은 **헤지 답변이 출처를 잃는 결함 자체는 없어졌다**는 것이다.

### 남는 위험 — 핵심 사실 판정이 여전히 문자열 매칭이다

세 회차의 실패는 모두 **핵심 사실 판정**이고 출처가 아니다. 실행마다 실패 문항이 바뀌는
것도 같은 이유다.

`NE-01`(학생식당 메뉴)을 직접 3회 호출해 보니 2회는 표준 문구 대신 "죄송하지만,
학생식당의 점심 메뉴에 대한 정보는 제공할 수 없습니다"로 답했다. 시스템 프롬프트가
"정확한 **규정**을 확인할 수 없습니다"로 지시하는데 식단은 규정이 아니라서 모델이
자연스럽게 바꿔 말하는 것으로 보인다. 문항의 기대 키워드가 이 표준 문구라 판정이 깨진다.

프롬프트 문구를 넓히거나 판정을 완화하는 선택지가 있지만, 둘 다 A·B 공동 계약
(`system.st`의 4원칙 · `GoldenSet` 기대값)에 닿으므로 혼자 바꾸지 않고 남겨 둔다.
